OpenDI Initiative (2024-Current)​

The Open Decision Intelligence initiative is an open source project working on interoperability standards for the Decision Intelligence (DI) industry.

I worked with one of the co-founders, Dr. Roberts, on the Coccidia Detection project, and he decided I'd be a good fit for helping them get this project started!

I've gotten to contribute a fairly eclectic bunch of solutions for various portions of a mostly web-based tech stack for this project. I set up most of the organization's GitHub repos, as well as all of OpenDI's public websites. They're all Docusaurus-based, serving markdown content via GitHub Pages (sound familiar?).

The main bulk of my work, though, has been architecting standards for interoperability. DI practices align around the concept of Causal Decision Diagrams (CDDs) and Causal Decision Models (CDMs). So interoperability in this sort of framework means being able to agree upon methods for storing and transmitting these models and diagrams, and to settle ideas around best practices, terminology, typical team members, roles and user stories, etc.

Why is this useful? This allows companies, researchers, and anyone else to specialize their role in DI, naturally encouraging an ecosystem of many tools created by many parties. The ideal situation is one where a CDD authored in one tool can be sent to another tool to have logical/simulation components attached, then connected to databases and simulated in yet another environment. Or a community could collaborate to build a model hub full of foundational decision models that can be freely extended in any toolset, adapted to more specific or complex contexts by experts, or used for research.

My work has largely been in laying foundations for this ecosystem. To that end, I have:

  • Created a JSON Schema for representing CDMs (with CDDs attached), using the JSON Schema standard
  • Specified standard API endpoints for transmitting model JSON, using OpenAPI 3.0
  • Contributed various bits of documentation and other content to our public sites
  • Helped build a community for OpenDI on Discord

On top of this foundation, I've also been implementing examples to demonstrate how the standards can be used:

  • I started a working Go implementation of our API specification
  • I created a browser-based prototype CDD authoring tool so you can graphically edit CDDs and see the JSON constructed in real-time
  • I joined the above two projects together with a database in a fully containerized Docker Compose project (repo), with Docker Hub images for the authoring tool and api

The screenshot at the top of this project section is the (work-in-progress) next step of the authoring tool: a browser-based decision engine with support for authoring, rendering, and simulating JavaScript decision logic, built with React.

481Engine - 2D Game Engine (2021-???)​

Flexible 2D game engine. Uses SFML for basic rendering, with a custom C++ backend.
Supports full game scripting via runtime-interpreted JavaScript.


2D Game Engine (C++, JavaScript)

Highlights​

  • Multithreaded subsystem architecture for division of engine tasks
  • Timekeeping for framerate-independent realtime game logic
  • Game Object model representation, using a hierarchical generic component system
  • Framework for constructing Game Objects and Scenes in JavaScript (using DukGlue)

Full Description​

I created the initial version of this engine for a class (CSC 481 - “Game Engine Foundations”) at NC State, over the course of a semester. This is a project I return to occasionally as time permits.

The engine backend (written in C++) provides a robust game loop and engine subsystem management architecture. 481Engine has separate subsystems for handling:

  • Rendering
  • Physics/collisions
  • Events
  • Game Object/Component logic.
    The engine is multithreaded; all physics calculations are performed on a separate thread.

481Engine supports complete game scripting. Game developers can use built-in components (Cameras, Colliders, rendering elements, etc.) to compose new Game Objects and Scenes, script per-frame-loop logic for those Game Objects and Scenes, construct Event handlers, and raise custom Events. This can all be done in JavaScript, utilizing the C++ backend code without having access to it.

At the request of the instructor, the backend code for this project lives in a private GitHub repository on my account. Contact me if you want to see the repo, or get the latest executable release.

Coccidia Detection (2022-2024)​

Applied computer vision for commercial poultry. I trained machine learning models to identify single-celled parasites (coccidia) in images taken from magnified slide samples of poultry feces. I handled software for this project, under the direction of Dr. David Roberts and Dr. Rocio Crespo at NC State. We published an article in Animals about the project.

Premise​

This was an instance segmentation project. The goal was to create lightweight models that workers in the poultry industry can use to analyze images taken from their field samples. A successfully-trained model should afford users the ability to:

  • Highlight instances of detected coccidia oocysts,
  • Classify each oocyst by species and sporulation status, and
  • Provide summaries about the number of each type of oocyst detected.

Sporulated oocysts have become infective. There is a slight visual distinction between sporulated and non-sporulated oocysts.

A field-ready tool made with this system could help alert workers to the presence of infective coccidia as early as possible, to prevent the spread of coccidiosis.

Model Training​

I adapted the existing Mask R-CNN framework, using the implementation offered in the Python library PixelLib, which makes the process very accessible. To make the most out of a smaller dataset, I implemented some custom data augmentation, with lots of incremental crops and rotations.

Animals Article​

We got an article published in Animals about this project. I was a co-author. This was my first exposure to academic writing, and I'm proud of how it turned out!

Read the article here.

I put together most of the charts and figures using a combination of pandas, Vega-Altair, and (good ol') GIMP. I drafted most of the Materials/Methods and Results sections, and had lots of smaller edits and additions throughout the other sections. Contact me for any questions related to this!

This was somewhat exploratory for LexisNexis, who was interested in targeting the Google Workspace ecosystem for smaller law firms who might be outside of the Office 365 ecosystem. My team of 4 adapted much of the expected CRM functionality into a Gmail add-on, targeting these main use cases:

Game AI - Monster Chase Demo (2022)​

This demo shows my implementation of the final project for a Game AI class taken at NC State in Spring 2022.


Game AI Pathfinding Demo (C++)

AI concepts demonstrated​

  • Decision and Behavior Trees
  • A* Pathfinding
  • Simple arrive/align

Full Description​

In this demo, a monster (the character with the dark purple path) chases a flee-er (the character with the green path), who runs away. This demonstrates pathfinding and path-following in a procedural grid-based environment.

The flee-er character's algorithm is slightly more sophisticated than a random wander algorithm. The flee-er divides the environment into sections, then moves between sections based on a decision tree. It initially seeks a section near one of the corners of the screen. Once there, it wanders using random short paths until it wanders out of the section. Then, depending on which non-corner section it wandered into, it picks a different corner section to move towards and then wander within.

The monster character's algorithm is more focused. It attempts to close distance to the flee-er by pathfinding to the euclidean midpoint between the current position and the intended goal position of the flee-er. Once it gets close enough, the monster begins pathfinding towards the flee-er directly. If the flee-er then escapes the monster by putting to much distance between the characters, the monster will express frustration by spinning in place, before resuming the chase. The monster's pursuit algorithm is handled by a behavior tree.

The monster and flee-er persist until the flee-er is inevitably caught.

fLight (Old Game Project) (~2016)​

I created this game for an introductory game development class in high school.


fLight (GameMaker)

fLight is a physics platformer with light puzzle elements. You control an eye-ball, whose ability to float recharges on contact with walls. The game explored different wall materials: bouncy, ultra-charging, wire-walls, etc. It featured the classic “shoot to move” idea had by many aspiring game developers. The player’s eyelid was procedurally animated based on velocity changes. Bullets reflected off of bouncy walls. Environment elements lit up when the player got close enough.

I had lots of fun making this on my own as a teen, and I learned plenty! An old WIP build of the game is still up on an old itch.io page, but I can’t guarantee it will run on anything.
